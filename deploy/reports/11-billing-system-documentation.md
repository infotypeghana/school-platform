## Overview

SchoolMS Ghana uses a **per-student, per-term** billing model with two payment gateways (Paystack and Moolre) and a complete financial safety layer covering webhook security, idempotency, and automated reconciliation.

---

## 1. Subscription Model

### Billing Cycle: Per Academic Term

Schools are billed once per academic term (approximately 3 times per year). The invoice amount is:

```
Amount = max(student_count, min_students) × price_per_student
```

Where:
- `student_count` = active students at time of invoicing
- `min_students` = package floor (prevents very low bills for large schools)
- `price_per_student` = set in `subscription_packages` table (managed by super admin)

### Subscription Packages

Packages are managed via `Super Admin → Packages`. Each package has:

| Field | Description |
|---|---|
| `name` | Display name (e.g. "School+") |
| `slug` | Machine slug (must contain one of: basic, starter, standard, growth, premium, enterprise) |
| `price_per_student` | GHS per student per term |
| `min_students` | Minimum billable student count |
| `billing_cycle` | `term` or `annual` |
| `features` | JSON array of feature labels (informational) |

**Feature tier resolution:** The FeatureGate service resolves plan tier from the package slug (e.g. `school-plus-premium` → `premium`).

## 2. Payment Gateways

### 2.1 Paystack

**Init flow:**
1. `POST /billing/pay` → `BillingController::initiate()` → `PaystackGateway::initialize()`
2. Paystack API call: `POST https://api.paystack.co/transaction/initialize`
3. Redirect to `authorization_url`
4. On success: Paystack redirects to `GET /billing/callback?reference=xxx`
5. `BillingController::callback()` verifies via `PaystackGateway::verify()`

**Webhook flow:**
1. Paystack POSTs to `/webhooks/paystack`
2. `PaystackWebhookController::handle()`:
   - Verifies HMAC-SHA512 signature (`X-Paystack-Signature`)
   - Checks `isPayloadFresh()` — rejects payloads older than 5 minutes
   - Checks Redis idempotency key — rejects duplicate references
   - Calls `SubscriptionService::activateFromPayment()`

### 2.2 Moolre

**Init flow:**
1. `POST /billing/pay` → `MoolreGateway::initialize()` with `state: starter`
2. Redirect to `authorization_url`
3. On success: verify with `state: confirm`

**Webhook flow:**
1. Moolre POSTs to `/webhooks/moolre`
2. `MoolreWebhookController::handle()`:
   - Verifies HMAC-SHA256 signature (`X-Moolre-Signature`)
   - Strict comparison: `$status !== 1` (not type-coercing `!= 1`)
   - Calls `SubscriptionService::activateFromPayment()`

## 3. Financial Safety Layer

### 3.1 Webhook Replay Prevention

```php
// Paystack — 5-minute timestamp window
private function isPayloadFresh(int|string $createdAt): bool {
    $ts = is_int($createdAt) ? $createdAt : strtotime((string) $createdAt);
    return (time() - $ts) <= 300; // MAX_DELIVERY_AGE_SECONDS
}

// Redis idempotency key — 30-minute deduplication window
$idempotencyKey = 'webhook:paystack:' . $reference;
if (! Cache::add($idempotencyKey, 1, now()->addMinutes(30))) {
    return response('OK', 200); // duplicate — silently accept
}
```

### 3.2 Duplicate Payment Prevention

At the application layer (before gateway call):
```php
if ($subscription->payments()->where('status', 'success')->exists()) {
    return redirect()->back()->with('info', 'Subscription is already active.');
}
```

### 3.3 Payment Audit Trail

Every payment (initiation, success, failure) writes to the `payments` table:

| Column | Value |
|---|---|
| `reference` | Unique gateway reference |
| `gateway` | `paystack` \| `moolre` |
| `amount` | GHS amount |
| `status` | `pending` \| `success` \| `failed` |
| `tenant_id` | FK to tenant |
| `subscription_id` | FK to subscription |
| `gateway_data` | JSON raw response |
| `created_at` | UTC timestamp |

### 3.4 Reconciliation Engine

**Weekly automated check (`payments:reconcile` — Sunday 04:00 WAT):**
- Orphaned payments: success with no subscription_id
- Duplicate references: same reference appearing 2+ times
- Unactivated subscriptions: active status but no success payment

**Auto-heal:** `--heal` flag links orphaned payments to the tenant's most recent subscription and activates it.

## 4. Invoice System

Invoices are generated by `GenerateTermInvoicesCommand` (1st of each month at 07:00) or manually via `Super Admin → Invoices → Generate`.

### Invoice Fields

| Field | Description |
|---|---|
| `invoice_number` | Sequential, e.g. `INV-2026-0001` |
| `tenant_id` | School |
| `subscription_id` | Linked subscription |
| `amount` | Total billable amount (GHS) |
| `status` | `draft` \| `sent` \| `paid` \| `void` |
| `due_date` | Payment due date |
| `notes` | Optional text |
| `paid_at` | Timestamp when marked paid |

### Invoice Operations

| Action | Route | Effect |
|---|---|---|
| View all | `GET /superadmin/invoices` | Paginated list |
| Generate | `POST /superadmin/invoices/generate` | Runs GenerateTermInvoicesCommand |
| Mark paid | `POST /superadmin/invoices/{id}/mark-paid` | Sets paid_at, activates subscription |
| Void | `POST /superadmin/invoices/{id}/void` | Nullifies invoice |

## 5. Grace Period Logic

After a term's `end_date`:
1. `CheckSubscriptionStatusJob` detects active/trial subscriptions past end_date
2. Transitions to `grace` (5 days configurable via `BILLING_GRACE_DAYS`)
3. Admin sees non-dismissible payment banner
4. Public website sees dismissible banner
5. After grace expires: transitions to `locked`
6. On payment: `transitionToActive()` → subscription is active for new term
